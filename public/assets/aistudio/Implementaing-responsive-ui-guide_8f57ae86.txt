Follow the workflow below **in the exact order specified**.

# PHASE 5 — IMPLEMENT THE RESPONSIVE SYSTEM

Now transform the existing website into a **fluid, content-driven, viewport- and container-aware responsive system**.

The goal is NOT to create separate fixed layouts for desktop, tablet and mobile.

The goal is to create **one adaptive design system** that continuously responds to the space actually available.

---

## CORE RESPONSIVENESS PRINCIPLE

Follow this rule throughout the entire implementation:

> **Do not make the website fit predefined devices. Make the website continuously adapt itself to the space that is actually available.**

The interface must respond intelligently to:

* Available width
* Available height
* Container width
* Container height
* Aspect ratio
* Orientation
* Content size
* Text length
* Input capability
* Available interaction space

Do not depend primarily on device identity.

---

# 1. PRESERVE THE EXISTING DESIGN

Do not unnecessarily redesign the website.

Preserve the existing:

* Branding
* Colors
* Typography hierarchy
* Visual identity
* Content
* Icons
* Images
* Components
* Functionality
* Navigation logic
* User flows
* Animations
* Interactions

unless a change is required to achieve proper responsiveness.

The purpose is to make the existing design **adaptable**, not to replace it with a new design.

---

# 2. UNIFY DEVICE-SPECIFIC VERSIONS WHERE APPROPRIATE

If the existing project has separate desktop/tablet/mobile implementations, determine which differences are actually necessary.

Where possible, consolidate them into reusable responsive components.

Do not remove a device-specific variation if it represents a genuine structural or usability requirement.

Convert unnecessary device-specific differences into:

* Fluid sizing
* Flexible wrapping
* Container-aware layouts
* Intrinsic sizing
* Dynamic alignment
* Responsive component states

---

# 3. FLUID SIZING

Prefer fluid sizing instead of excessive fixed dimensions.

Use appropriate combinations of:

```text
%
rem
em
vw
vh
dvw
dvh
clamp()
min()
max()
minmax()
auto
fit-content
```

Use fixed pixel values only where they are genuinely appropriate, such as:

* Borders
* Small icon dimensions
* Specific control constraints
* Technical requirements
* Intentional fixed visual details

Do not create large collections of arbitrary pixel values for different screen widths.

---

# 4. FLUID TYPOGRAPHY

Make typography responsive.

Use fluid typography such as:

```css
font-size: clamp(min, preferred, max);
```

where appropriate.

Adapt:

* Headings
* Body text
* Labels
* Navigation text
* Button text
* Modal text
* Notification text
* Form text

Maintain the existing hierarchy and readability.

Do not allow text to become:

* Too small
* Too large
* Clipped
* Overlapping
* Unnecessarily wrapped

---

# 5. CONTAINER-AWARE RESPONSIVENESS

Prefer **container queries** for reusable components whenever appropriate.

A component should respond to the space available to it rather than assuming that the entire viewport is available.

This is especially important for:

* Cards
* Widgets
* Sidebars
* Dashboard components
* Forms
* Tables
* Modals
* Reusable content blocks

---

# 6. FLEXIBLE LAYOUT

Use:

* CSS Grid
* Flexbox
* Intrinsic sizing
* `minmax()`
* `auto-fit`
* `auto-fill`
* Wrapping
* Content-aware sizing

Avoid unnecessary absolute positioning.

If absolute or fixed positioning already exists, determine whether it is intentional before changing it.

---

# 7. ORIENTATION RESPONSIVENESS

The website must work correctly in:

* Portrait
* Landscape

Do not simply scale the portrait layout into landscape.

Allow layouts to intelligently reflow when the available aspect ratio changes.

---

# 8. VIEWPORT HEIGHT RESPONSIVENESS

Do not consider width alone.

A layout must also adapt to changes in viewport height.

Account for:

* Short browser windows
* Tall screens
* Mobile browser UI
* Virtual keyboard appearance
* Resized windows
* Split-screen mode

Avoid unnecessary fixed viewport-height assumptions.

---

# 9. POPUPS, MODALS AND DIALOGS

Every existing popup/modal/dialog must be individually checked.

They must adapt to the available viewport.

Ensure:

* No clipping
* No inaccessible buttons
* No content extending outside the viewport
* No accidental horizontal overflow
* Proper scrolling when content exceeds available height
* Proper button wrapping/stacking
* Correct close-button positioning
* Correct internal spacing
* Correct typography

The popup itself must also be responsive, not merely the page behind it.

---

# 10. DROPDOWNS AND POPOVERS

Every existing dropdown/popover must adapt to available space.

Ensure they:

* Stay within the usable viewport where appropriate
* Do not cover critical controls unnecessarily
* Reposition when there is insufficient space
* Handle long content
* Remain usable on touchscreens

---

# 11. NOTIFICATIONS AND TOASTS

Every existing notification/toast/alert must be checked.

Ensure that notifications:

* Remain readable
* Do not overflow
* Do not cover essential controls unnecessarily
* Adapt their width
* Wrap text correctly
* Maintain accessible buttons
* Respect safe areas
* Work in portrait and landscape

---

# 12. FORMS AND CONTROLS

Inputs, buttons and controls must:

* Remain usable
* Maintain appropriate touch targets
* Wrap or stack when necessary
* Avoid overflow
* Preserve alignment
* Handle long labels
* Handle validation messages
* Handle keyboard interaction

# 13. TABLES AND DATA-DENSE COMPONENTS

For narrow containers, determine the most appropriate existing-project-compatible behavior, such as:

* Responsive wrapping
* Horizontal scrolling where genuinely necessary
* Column prioritization
* Stacked presentation
* Alternative compact representation

Do not destroy data visibility merely to avoid scrolling.

# 19. BREAKPOINT POLICY

Breakpoints are allowed.

However:

> **Use breakpoints for behavioral/structural changes, not as a substitute for fluid responsive design.**

Do not create dozens of arbitrary breakpoints.

Do not assume:

```text
320px = mobile
768px = tablet
1024px = tablet
1280px = desktop
```

These may be useful thresholds, but they must not define the entire responsive architecture.

The website must remain fluid between, below and above any breakpoints.

Every major reusable component should be able to adapt independently to the space available to it.

Do not solve a component's responsiveness only by adding page-level media queries if the component itself can be made adaptive.

Prefer reusable responsive behavior.

# MOST IMPORTANT IMPLEMENTATION RULE

Throughout the entire process, follow this principle:

> **The website should not be designed for a list of devices. It should be designed for the space available to the website at any given moment.**

Think of responsiveness as a **continuous spectrum**, not:

```text
Mobile → Tablet → Desktop
```

Instead, think:

```text
Available space changes continuously
                ↓
Components continuously adapt
                ↓
Layout continuously reflows
                ↓
Typography and spacing continuously adjust
                ↓
The interface remains usable and visually coherent
```

Do not stop at making the website responsive at common device sizes.

Make the underlying implementation **intrinsically responsive** so that it continues to behave correctly at unexpected viewport dimensions.
